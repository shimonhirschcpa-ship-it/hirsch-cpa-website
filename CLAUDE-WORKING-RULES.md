# Shimon's standing rules

He set these on 26 August 2026 and wants them to survive every reset, update
and account change.

1. Read it back first. Whenever he asks for something, restate it in your own
   words before acting, so it is clear you agree on what he meant. Never skip
   this, even when the request seems obvious.

2. App or portal changes go through three stops. First read the request back.
   Second, after he confirms, investigate and report whether it is safe and
   how it would work. Third, only build after he gives an explicit go-ahead.

3. Website changes: show it first. Produce an HTML preview of how the change
   will look. Only build after he approves the look. Previews must be a single
   self-contained HTML file or PNG images. Multi-file previews do not reach
   him.

4. No code changes without approval. Never modify, write or commit code
   without his explicit approval. Investigate, present a plan, then wait. This
   was violated once and he does not tolerate it.

5. Short, plain English. No jargon, no long explanations, no file paths.

6. The hosting and plan risks lead every to-do list. Whenever he asks for any
   to-do list, those go first, before the project's own items. He asked for
   this after his portal went down from a database pause.

7. Email through the connector, never the browser. Opening a tab to read his
   mail annoys him.

8. In his browser: open one tab, use it, close it. Do not create tab groups.
   Leave his own tabs alone.

9. Reuse existing code sessions instead of spawning new ones. He has set
   permissions on the sessions already open and a fresh one makes him
   re-approve everything. If a new session really is the better call, say so
   and explain why rather than doing it silently.

10. To-do lists must not trigger permission popups. The flow is exactly: he
    asks, you read it back in one line, he says good, it is written. Nothing
    else interrupts him.

11. Mark items done automatically. When work ships, move the item to Done in
    the same pass, without being asked. Never leave a shipped item open and
    never ask permission to close a finished one.

## Why these exist

An earlier update wiped all shared context, including to-do lists that only
existed in conversation. Separately, code was changed without his approval. He
asked for both to be written down so neither repeats.

## Mistakes that must not repeat

- He asked for his to-do list and got a code audit instead. He keeps real list
  files. Read them. Do not synthesise.
- He was told there was no demo app. There was one, a fourth hosting project
  invisible in the local code. Absence from the code is not evidence of
  absence. Check the dashboard.
- Two sessions edited the website repo at the same time and garbled text went
  live. One session per repo.
